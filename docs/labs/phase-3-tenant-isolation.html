Phase 3: Tenant isolation

Stark Industries moves in next door to Acme, and the walls go up: namespaces, Quotas, RBAC, and network policy. Ticket #5.

Goal: two Tenants share dc-east without seeing, starving, or reaching each other. Acme's chat moves out of the default namespace into its own. Stark's jarvis arrives, asks for more than its Quota allows, and gets told no. An Acme admin gets a kubeconfig that cannot touch Stark. A default-deny network policy stops chat pods from reaching jarvis while ingress-nginx still can.

Two folders, one boundary (ADR-0003). Tenants own what runs: deploy/tenants/<tenant>/. The Infra Admin owns the walls and the capacity: infra/tenants/<tenant>/. In this lab you play both, so keep track of which hat you are wearing.

You wantKubernetes objectAWS twin
A boundary Tenants cannot see acrossNamespaceA separate account, or a separate ECS cluster
A ceiling on what a Tenant can reserveResourceQuotaA capacity provider's auto scaling group maximum
Defaults and per-container maximumsLimitRangeNo twin: a task definition must state a size, so nothing fills one in
An admin who can only touch their own TenantServiceAccount, Role, RoleBindingAn IAM role with a policy scoped by resource
Pods that cannot talk across TenantsNetworkPolicySecurity groups

Before you start

Prerequisite: phase 2's end state in dc-east (chat on 0.1.1 with probes, resources, and an HPA, all in the default namespace, ingress-nginx answering on 8080). Confirm it:

kubectl --context kind-dc-east get deploy,svc,ingress,hpa -l tenant=acme

Start the command journal in this terminal. It writes to the gitignored .journal/phase-3.log and records only this terminal:

source scripts/lab-journal.sh start phase-3

Step 1: Namespaces, the first wall

Everything so far landed in default, which is where objects go when nobody says otherwise. A namespace is a named scope for objects: names only have to be unique inside it, and every wall in this lab attaches to it. Wearing the Infra Admin hat, create infra/tenants/acme/namespace.yaml:

apiVersion: v1
kind: Namespace
metadata:
  name: tnt-acme
  labels:
    forge.io/tenant: acme

And infra/tenants/stark/namespace.yaml, the same shape with tnt-stark and stark. Apply both:

kubectl --context kind-dc-east apply -f infra/tenants/acme/namespace.yaml -f infra/tenants/stark/namespace.yaml
kubectl --context kind-dc-east get namespaces --show-labels
Expected output

Your two namespaces beside default, ingress-nginx, kube-system, and the others Kubernetes runs for itself.

With no -n flag, which namespace does this list, and how many chat pods does it show?

kubectl --context kind-dc-east get pods
Expected output

The two chat pods. Without -n, kubectl uses the namespace in your context, which is default. Nothing has moved yet.

What a namespace is not

A namespace is a scope, not a wall by itself. Pods in tnt-acme can still reach pods in tnt-stark, and a kubeconfig with cluster-admin rights sees everything. The Quota, the Role, and the NetworkPolicy in the steps ahead are what turn the scope into a boundary. Nodes, namespaces themselves, and a few other objects are cluster-scoped and live in no namespace at all.

Step 2: Move chat into tnt-acme

Acme's six files in deploy/tenants/acme/ say nothing about a namespace, which is why chat landed in default. Add one line under metadata: in every file, at the same indent as name::

  namespace: tnt-acme

Now apply the folder and watch what happens to the Ingress:

For a moment, two Ingresses will claim the hostname chat.acme.dc-east.localtest.me, one in default and one in tnt-acme. What does ingress-nginx do with the second one?

kubectl --context kind-dc-east apply -f deploy/tenants/acme/
Expected output

Five objects created in tnt-acme, then a refusal from an admission webhook, a check the API server hands to ingress-nginx before it stores an Ingress:

Error from server (BadRequest): error when creating "deploy/tenants/acme/chat-ingress.yaml": admission webhook "validate.nginx.ingress.kubernetes.io" denied the request: host "chat.acme.dc-east.localtest.me" and path "/" is already defined in ingress default/chat

The webhook refuses a second claim on a hostname rather than letting two Ingresses fight over it. Meanwhile the new chat pods are starting in their new home, and the old ones still serve Acme:

kubectl --context kind-dc-east -n tnt-acme get pods
Expected output

Two chat pods, Running 1/1 once the model loads.

Retire the old objects. Every Acme object carries the tenant=acme label, so one command finds them all:

kubectl --context kind-dc-east -n default delete deploy,svc,ingress,hpa,configmap,secret -l tenant=acme

With the hostname free, apply again:

kubectl --context kind-dc-east apply -f deploy/tenants/acme/
Expected output

Five objects unchanged (the Secret says configured, as always) and the Ingress created.

curl http://chat.acme.dc-east.localtest.me:8080/readyz
Expected output

{"status":"ready","model":"acme-chat-1"}. For up to several seconds after the apply, nginx still routes the old, deleted Ingress and answers 502, then reloads and serves 200. Retry until it does.

kubectl --context kind-dc-east get all -n default
Expected output

Only the kubernetes Service. Acme has left the building.

Why the migration had a gap

Between the delete and the second apply, nginx had no route for the hostname and answered 404, and for a few seconds after the apply it answered 502 while it reloaded. Zero-downtime moves across namespaces need a second hostname or a router in front, which is the Global Entry Point's job in phase 4. Here the gap was a few seconds, and the point was to see the conflict.

Step 3: A ceiling for Acme

A ResourceQuota adds up what a namespace has reserved and refuses anything that would push a total past its ceiling. Create infra/tenants/acme/quota.yaml:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: tenant-quota
  namespace: tnt-acme
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    pods: "10"

Chat at its HPA maximum of six pods reserves 600m of CPU and 768Mi of memory, so Acme has room to grow inside this ceiling. Pair it with a LimitRange, infra/tenants/acme/limitrange.yaml, which fills in requests and limits for any container that forgets to ask, and caps what one container may ask for:

apiVersion: v1
kind: LimitRange
metadata:
  name: tenant-limits
  namespace: tnt-acme
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: 500m
        memory: 256Mi
      max:
        cpu: "2"
        memory: 2Gi
kubectl --context kind-dc-east apply -f infra/tenants/acme/quota.yaml -f infra/tenants/acme/limitrange.yaml

The Quota reports what Acme has used. Right after chat moved in with two pods, what number sits in the requests.cpu Used column?

kubectl --context kind-dc-east -n tnt-acme describe quota tenant-quota
Expected output

Five rows, alphabetical: limits.cpu 1 of 4, limits.memory 512Mi of 4Gi, pods 2 of 10, requests.cpu 200m of 2, requests.memory 256Mi of 2Gi. Two pods at 100m and 128Mi requests and 500m and 256Mi limits: phase 2's numbers are now the currency of the Quota.

Now the LimitRange at work. Start a pod that asks for nothing:

kubectl --context kind-dc-east -n tnt-acme run tester --image=curlimages/curl --restart=Never -- sleep 300
kubectl --context kind-dc-east -n tnt-acme get pod tester -o jsonpath='{.spec.containers[0].resources}{"\n"}'
Expected output

The pod carries requests of 100m and 128Mi and limits of 500m and 256Mi that you never wrote. The LimitRange filled them in at admission, the API server's checks on a request before it stores the object.

Why a Quota without a LimitRange rejects pods

Once a Quota constrains requests and limits, the API server refuses any pod in that namespace that does not state them, because it cannot add an unknown to the total. To see it: delete the tester pod (the command below), delete the LimitRange, run the tester command again, and you get:

Error from server (Forbidden): pods "tester" is forbidden: failed quota: tenant-quota: must specify limits.cpu for: tester; limits.memory for: tester; requests.cpu for: tester; requests.memory for: tester

The LimitRange's defaults are what keep Tenants from hitting that wall by accident. In ECS terms, the task definition always states a size, so this trap never existed there. Re-apply the LimitRange if you tried it.

kubectl --context kind-dc-east -n tnt-acme delete pod tester

Step 4: jarvis moves in and hits the wall

Put on the Tenant hat. Stark's jarvis is a batch summarizer: slower per request, and sized generously by an engineer who never read the Quota. It runs a newer build of fake-inference. Build and load it:

docker build -t forge/fake-inference:0.1.2 --build-arg APP_VERSION=0.1.2 services/fake-inference/
kind load docker-image forge/fake-inference:0.1.2 --name dc-east

Create deploy/tenants/stark/jarvis-config.yaml:

apiVersion: v1
kind: ConfigMap
metadata:
  name: jarvis-config
  namespace: tnt-stark
  labels:
    tenant: stark
data:
  MODEL_NAME: stark-jarvis-1
  SIMULATED_DELAY_MS: "800"
  BURN_CPU_MS: "0"

And deploy/tenants/stark/jarvis-deployment.yaml, chat's shape with Stark's names and a request of one whole CPU and 1Gi per pod:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: jarvis
  namespace: tnt-stark
  labels:
    app: jarvis
    tenant: stark
spec:
  replicas: 2
  selector:
    matchLabels:
      app: jarvis
  template:
    metadata:
      labels:
        app: jarvis
        tenant: stark
    spec:
      containers:
        - name: fake-inference
          image: forge/fake-inference:0.1.2
          ports:
            - containerPort: 8000
          envFrom:
            - configMapRef:
                name: jarvis-config
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 2
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 15
            periodSeconds: 5
            failureThreshold: 3
          resources:
            requests:
              cpu: "1"
              memory: 1Gi
            limits:
              cpu: "1"
              memory: 1Gi
kubectl --context kind-dc-east apply -f deploy/tenants/stark/

Stark's Quota allows 1500m of CPU requests. Each jarvis pod asks for 1000m. How many pods start, and where will you find the rest?

kubectl --context kind-dc-east -n tnt-stark get deploy,pods
Expected output

The Deployment sits at 1/2 and only one pod exists. Nothing is Pending, because the second pod was never created: the Quota refuses it at admission, before the scheduler ever sees it. That silence is why Quota failures go unnoticed.

The refusal is recorded as an event on the object that tried, the ReplicaSet. Events are namespaced objects of their own, so ask for them directly:

kubectl --context kind-dc-east -n tnt-stark get events --field-selector reason=FailedCreate
Expected output 
Error creating: pods "jarvis-76b546b58b-4xpcp" is forbidden: exceeded quota: tenant-quota, requested: requests.cpu=1,requests.memory=1Gi, used: requests.cpu=1,requests.memory=1Gi, limited: requests.cpu=1500m,requests.memory=1536Mi

Several rows, all with that message. Requested plus used would pass limited, so the pod was refused. The ReplicaSet keeps retrying, and the delay between retries doubles after every refusal.

kubectl --context kind-dc-east -n tnt-stark describe quota tenant-quota
Expected output

Used 1 of 1500m CPU and 1Gi of 1536Mi memory. One more pod of the same size would need 2 and 2Gi.

Why the ECS version of the Quota wall is quieter still

ECS has no per-Tenant reservation ceiling inside a cluster. A task that does not fit stays in PROVISIONING or the service event log says it could not place it, and the fix is more capacity. Kubernetes lets the Infra Admin say "this Tenant gets this much" and makes the Tenant resize, which is exactly the Quota Request conversation from ADR-0003.

Docs: Resource Quotas: compute resources · kubectl get events

Step 5: Resize jarvis and roll it out

Stark's engineer files a Quota Request and the Infra Admin says no: jarvis does not need a whole CPU to sleep for 800 milliseconds. Resize it. In jarvis-deployment.yaml change the requests to cpu: 500m and memory: 512Mi, leave the limits, then apply and watch:

Two pods at 500m fit inside 1500m. Will the rollout complete?

kubectl --context kind-dc-east apply -f deploy/tenants/stark/jarvis-deployment.yaml && kubectl --context kind-dc-east -n tnt-stark rollout status deployment/jarvis --timeout=30s
Expected output

It does not. rollout status times out with "1 out of 2 new replicas have been updated", and get deploy jarvis shows READY 2/2 next to UP-TO-DATE 1: the old one-CPU pod plus one new pod, both serving, and the rollout stuck between them.

kubectl --context kind-dc-east -n tnt-stark get deploy jarvis && kubectl --context kind-dc-east -n tnt-stark get events --field-selector reason=FailedCreate
Expected output

A fresh refusal: the second new pod would need 500m on top of the 1000m the old pod holds and the 500m the first new pod holds, and 2000m passes 1500m.

This is the second wall, and it is a subtler one. Phase 2's rolling update creates before it destroys: with two replicas it may surge one extra pod and may not retire an old one until two new pods are available. The surge pod took Stark's last 500m. The second new pod needs Quota the old pod still holds, and the old pod cannot go first. A Tenant at its ceiling cannot surge; it has to replace. Tell the Deployment so, in jarvis-deployment.yaml under spec:, at the same indent as replicas::

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 0
      maxUnavailable: 1
kubectl --context kind-dc-east apply -f deploy/tenants/stark/jarvis-deployment.yaml && kubectl --context kind-dc-east -n tnt-stark rollout status deployment/jarvis --timeout=180s
Expected output

The old pod goes first, the second new pod fits, and the rollout completes: 2/2, UP-TO-DATE 2, Used 1 of 1500m. If you spent a while reading before this apply, the ReplicaSet's retry delay has grown with every refusal and the wait can pass three minutes; run rollout status again rather than assuming a failure, or force a fresh ReplicaSet with no backoff: kubectl --context kind-dc-east -n tnt-stark rollout restart deployment/jarvis.

Why this matters more for inference than for web apps

A surge rollout borrows capacity for a moment. Web tiers usually have it. A GPU fleet usually does not: every accelerator is allocated, and a model server that needs a whole GPU cannot surge into a spare one that does not exist. Replace-in-place rollouts, with a brief dip in capacity, are how capacity-bound serving fleets roll. ECS says the same thing with minimumHealthyPercent 50 and maximumPercent 100.

Step 6: An Acme admin who cannot see Stark

So far every command ran as the cluster admin kind gave you. Tenants do not get that. Kubernetes has no user objects; it trusts whatever the API server's authentication says and then asks RBAC what that identity may do. For a Tenant admin we use a ServiceAccount, a Role listing the verbs it may use on which resources in one namespace, and a RoleBinding tying the two together. Infra Admin hat on. Create infra/tenants/acme/rbac.yaml:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: acme-admin
  namespace: tnt-acme
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: tenant-admin
  namespace: tnt-acme
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log", "services", "configmaps", "secrets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: ["autoscaling"]
    resources: ["horizontalpodautoscalers"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["resourcequotas", "limitranges"]
    verbs: ["get", "list"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["networkpolicies"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: acme-admin
  namespace: tnt-acme
subjects:
  - kind: ServiceAccount
    name: acme-admin
    namespace: tnt-acme
roleRef:
  kind: Role
  name: tenant-admin
  apiGroup: rbac.authorization.k8s.io

Read the Role as ADR-0003 in YAML: a Tenant owns its Services and can read, but not change, its Quota and its NetworkPolicies. One rule per API group, because a rule that lists several groups and several resources grants every combination, and auth can-i --list would show nonsense such as ingresses.autoscaling.

kubectl --context kind-dc-east apply -f infra/tenants/acme/rbac.yaml

Mint a token for the ServiceAccount and build a kubeconfig around it. Start from your own, then swap the credentials out. The file name ends in .kubeconfig, which the repo's gitignore already covers:

TOKEN=$(kubectl --context kind-dc-east -n tnt-acme create token acme-admin --duration=8h)
kubectl config view --minify --context kind-dc-east --flatten > acme.kubeconfig
kubectl --kubeconfig acme.kubeconfig config set-credentials acme-admin --token="$TOKEN"
kubectl --kubeconfig acme.kubeconfig config set-context kind-dc-east --user=acme-admin --namespace=tnt-acme
kubectl --kubeconfig acme.kubeconfig config unset users.kind-dc-east
Why the unset matters

--flatten copied your cluster-admin certificate into the new file. The unset removes it, so the file holds only the token and the cluster's public CA. Check with grep -c client-certificate-data acme.kubeconfig: the answer must be 0 before you would ever hand such a file to a Tenant. grep exits 1 when the count is 0, which is the answer you want, and the journal will record that exit code.

Now act as Acme:

kubectl --kubeconfig acme.kubeconfig get pods
Expected output

The two chat pods. The file's current context already names the cluster, the user, and tnt-acme, so neither --context nor -n is needed.

kubectl --kubeconfig acme.kubeconfig get pods -n tnt-stark
Expected output 
Error from server (Forbidden): pods is forbidden: User "system:serviceaccount:tnt-acme:acme-admin" cannot list resource "pods" in API group "" in the namespace "tnt-stark"

The identity is the ServiceAccount, spelled the way RBAC sees it.

Nodes belong to no namespace. Will the Acme admin be allowed to list them?

kubectl --kubeconfig acme.kubeconfig get nodes
Expected output 
Error from server (Forbidden): nodes is forbidden: User "system:serviceaccount:tnt-acme:acme-admin" cannot list resource "nodes" in API group "" at the cluster scope

A Role reaches only inside its namespace; cluster-scoped objects need a ClusterRole, which no Tenant gets.

kubectl --kubeconfig acme.kubeconfig auth can-i --list
Expected output

The Role's resources and verbs, plus rows every authenticated identity gets: the selfsubject* reviews, clustertrustbundles, and a list of non-resource URLs such as /healthz. This is the command to reach for when a Tenant asks "what am I allowed to do?"

Reading Stark was refused. Changing Stark must be too:

kubectl --kubeconfig acme.kubeconfig -n tnt-stark scale deployment jarvis --replicas=0
Expected output

Forbidden, naming the same ServiceAccount and the namespace tnt-stark. jarvis keeps its two replicas.

kubectl --kubeconfig acme.kubeconfig delete resourcequota tenant-quota
Expected output 
Error from server (Forbidden): resourcequotas "tenant-quota" is forbidden: User "system:serviceaccount:tnt-acme:acme-admin" cannot delete resource "resourcequotas" in API group "" in the namespace "tnt-acme"

Acme can read its ceiling and cannot move it.

Why a token and not a user

Production clusters authenticate humans through OIDC (Okta, Google, Entra) and map groups to RoleBindings; the Forge Console will fake that in phase 7 (ADR-0007). A ServiceAccount token is the built-in identity Kubernetes can mint on the spot, which makes it the right tool for a lab and for machine clients. This one expires in eight hours; mint another if the drill's preflight says so.

Step 7: Pods that cannot cross the hall

Inside a cluster every pod can reach every other pod by default. Prove that the wall is not there yet by curling jarvis's Service from inside Acme's namespace, using its cluster DNS name jarvis.tnt-stark:

kubectl --context kind-dc-east -n tnt-acme run tester --rm -i --quiet --restart=Never --image=curlimages/curl -- curl -sS -m 5 http://jarvis.tnt-stark/healthz
Expected output

Exactly {"status":"ok"}. Acme just talked to Stark's model server. The tester pod stands in for a chat pod: the policy you are about to write is evaluated on jarvis's side, so any pod in tnt-acme is the same test.

A NetworkPolicy selects pods and lists who may talk to them. A policy that selects every pod and allows nobody is the default-deny wall; further policies punch holes, and holes add up. Two holes are required: pods of the same Tenant, and ingress-nginx, or the front door stops working too. Create infra/tenants/acme/netpol.yaml:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: tnt-acme
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-tenant
  namespace: tnt-acme
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector: {}
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-nginx
  namespace: tnt-acme
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx

And infra/tenants/stark/netpol.yaml, identical with namespace: tnt-stark. Apply both:

kubectl --context kind-dc-east apply -f infra/tenants/acme/netpol.yaml -f infra/tenants/stark/netpol.yaml

The kubelet's readiness probes come from the node, not from a pod. Under default-deny, do chat and jarvis stay Ready?

kubectl --context kind-dc-east get pods -A -l tenant
Expected output

All four pods stay 1/1 Running. The kubelet's probes arrive from the node's own address on the pod network, and kind's plugin lets them through, so a default-deny policy does not take your pods out of service. Some plugins need an explicit hole for that; check the first time you turn on default deny anywhere new.

Now the wall:

kubectl --context kind-dc-east -n tnt-acme run tester --rm -i --quiet --restart=Never --image=curlimages/curl -- curl -sS -m 5 http://jarvis.tnt-stark/healthz
Expected output

Five seconds of silence, then curl: (28) Connection timed out after 5001 milliseconds, then kubectl reporting the pod terminated with an error. The wall drops the packet rather than refusing the connection, so a blocked path looks like a timeout. Without -m 5, curl would wait over two minutes.

And the two holes. Same Tenant still talks, and the front door still opens:

kubectl --context kind-dc-east -n tnt-stark run tester --rm -i --quiet --restart=Never --image=curlimages/curl -- curl -sS -m 5 http://jarvis/healthz
curl http://chat.acme.dc-east.localtest.me:8080/readyz && curl http://jarvis.stark.dc-east.localtest.me:8080/readyz
Expected output

{"status":"ok"} from inside Stark, then both ready lines through the ingress.

Where the wall is enforced

A NetworkPolicy is a request; the cluster's network plugin enforces it on each node, packet by packet, and a plugin that does not support policies silently allows everything. kind's plugin, kindnet, enforces them. Prove yours does:

kubectl --context kind-dc-east -n kube-system logs ds/kindnet | grep -i "policy engine"

Expect Policy engine is ready. On bare metal Forge would run Calico or Cilium for the same job. Security groups are the ECS twin: attached at the task's network interface, evaluated on the host, allow lists that add up.

The egress trap

These policies restrict Ingress only, so pods can still reach anything. A default-deny on Egress is stricter and bites in a way that surprises everyone once: it blocks the pod's DNS lookups too, so every hostname stops resolving until you add a hole for kube-dns on port 53. File that away for the day you tighten egress.

What you learned

  • A namespace is a scope. Quota, RBAC, and NetworkPolicy attach to it and turn it into a boundary.
  • Quota refusals happen at admission and show up as events, not as Pending pods. Requests and limits are the currency; a LimitRange keeps every pod paying in it.
  • A Tenant at its ceiling cannot surge. Replace-in-place rollouts (maxSurge: 0) are how capacity-bound fleets roll, GPU fleets included.
  • RBAC grants verbs on resources to an identity, inside one namespace for a Role. Nothing is allowed until something allows it.
  • NetworkPolicies are allow lists that add up on top of a default deny, enforced by the network plugin on each node. Same-Tenant traffic and ingress-nginx need explicit holes.
  • Two folders mark the boundary from ADR-0003: Tenants own deploy/, the Infra Admin owns infra/.
  • kubectl diff compares live objects with your files, which is how you find drift without reading YAML by eye.

Check yourself

1. Acme's admin runs kubectl get nodes with the acme kubeconfig and is refused. Why, when the Role grants list?

A Role and RoleBinding grant rights inside one namespace. Cluster-scoped objects such as nodes and namespaces need a ClusterRole, which no Tenant receives.

2. jarvis asked for two pods and got one. Where did the second one go?

Quota is enforced when the pod is created, before scheduling. The pod never exists, so nothing is Pending; the ReplicaSet's FailedCreate event is the only trace.

3. Why does the lab pair every ResourceQuota with a LimitRange?

The API server cannot add an unknown to a total, so a Quota on requests.cpu rejects pods with no CPU request. The LimitRange's defaults keep that from becoming a trap for every tester pod and one-off job.

4. After default-deny in tnt-acme, requests through the ingress still work. Which policy makes that true?

The controller is a pod in the ingress-nginx namespace, so its traffic is pod traffic and default-deny would block it. The namespaceSelector hole is what keeps the front door open, and the drill breaks exactly that.

5. Two Ingresses claim the same hostname during the move. What did ingress-nginx do?

The validating webhook rejects an Ingress whose host and path are already defined by another Ingress, which is why the first apply left the new Ingress uncreated and the second apply, after the delete, succeeded.

6. Which command tells you, in one shot, which live object no longer matches the files under infra/tenants/?

kubectl diff sends each file through a server-side dry run and prints a unified diff against the live object, exiting 1 when anything differs; -R is what makes it descend into the tenant folders. A client dry run only validates the files; get and describe show live state without comparing it.
