Phase 0: Boot the data centers

Two running Kubernetes clusters, dc-east and dc-west, each with one control-plane node and two workers standing in for bare-metal hosts. Ticket #2.

At the end, kubectl can talk to either data center. You type every command in this lab yourself. Expected results follow the important ones.

Before you start

Docker Desktop must be running with WSL integration enabled for this distro. Verify:

docker info --format '{{.ServerVersion}}'
Expected output

A version number means you are ready. An error mentioning "this WSL 2 distro" means: Docker Desktop, Settings, Resources, WSL integration, enable this distro, Apply & Restart.

Start the command journal in this terminal. It records each command you type, with its exit code, into .journal/phase-0.log at the repo root. The file is gitignored and never leaves your machine. It lets the phase-done review see where you retried or hit an error the lab did not expect.

source scripts/lab-journal.sh start phase-0
Why source instead of running it

The script installs a hook in the shell you are typing in, which only a sourced script can do. Only this terminal is recorded. Stop it at the end of the lab with source scripts/lab-journal.sh stop.

Step 1: Install the tools

./scripts/00-install-tools.sh

The script installs three binaries into ~/.local/bin and is safe to re-run.

What the three binaries do
  • kubectl: the CLI for any Kubernetes API server. In ECS terms this is the aws ecs CLI, except the same binary works against every Kubernetes cluster anywhere.
  • kind: runs Kubernetes clusters in which every "machine" is a Docker container.
  • helm: a package manager for Kubernetes manifests. You will meet it in phase 5.

Verify:

kind version && kubectl version --client && helm version --short

Step 2: Read the data center config

Open infra/kind/dc-east.yaml. Things to notice:

  • Each entry under nodes: becomes one Docker container running its own kubelet and container runtime. These containers are our bare-metal hosts.
  • The control-plane node will run the cluster's brain: API server, etcd, scheduler, controller manager. ECS and Cloud Run hide this half from you. Here you get to watch it work.
  • extraPortMappings publishes the control-plane node's ports 80 and 443 to your host as 8080 and 8443. That is the door traffic will use to enter dc-east in phase 1.
  • The worker labels name a rack and zone, so later phases can schedule against topology.

Docs: kind configuration

Step 3: Create dc-east

How many Docker containers will this command create? The config file you just read says.

kind create cluster --config infra/kind/dc-east.yaml
Expected output

The "Preparing nodes" line shows three package icons, one per node. Step 4 shows the same three as containers.

The first run pulls the node image and takes a few minutes. When it finishes:

kubectl cluster-info --context kind-dc-east
Why the context is called kind-dc-east

kind wrote credentials into ~/.kube/config under the context name kind-dc-east. A context bundles cluster, user, and namespace. Think of an AWS CLI profile plus region in one name.

Your "bare metal":

The same machines, as Kubernetes sees them:

On your own: Create dc-west

Goal: the second data center exists, its three nodes are Ready, and kubectl has a context for it. Its config is infra/kind/dc-west.yaml. Read it first: which host ports does dc-west publish, and why can they not be the same as dc-east's?

You did the same thing for dc-east two steps ago. Try it from memory, then prove it:

kubectl config get-contexts
Expected output

Two contexts, kind-dc-east and kind-dc-west.

kubectl --context kind-dc-west get nodes
Expected output

Three nodes, all Ready within a minute or two.

Show the commands 
kind create cluster --config infra/kind/dc-west.yaml
Why dc-west publishes 9080 and 9443

Both data centers live on the same laptop, and dc-east already holds 8080 and 8443. Two clusters cannot publish the same host port, so dc-west takes the next pair.

Why the labs always pass --context

kubectl config use-context switches the default, but the labs pass --context explicitly so the two data centers never blur.

Drill: something is wrong in dc-east

On call, nobody tells you which layer broke. This drill injects one fault into dc-east, chosen at random from a small set. Your job is to find it with the commands from this lab and fix it. You type the break command yourself, and it changes only dc-east and your kubeconfig.

scripts/drills/phase-0.sh break

Give it a minute, then run the checkpoint commands again. Before opening any hint, say in one sentence what you see. That sentence is the symptom, and it decides where you look next.

Hint 1: where to look

Two layers can fail here. If kubectl itself errors before showing anything, the problem sits between you and the API server: the kubeconfig. If kubectl answers but a node is not Ready, the problem is that machine. In ECS terms: a broken CLI profile versus a container instance that stopped reporting.

Hint 2: what to run 
kubectl --context kind-dc-east get nodes
kubectl --context kind-dc-east describe node NODE | grep -A8 Conditions
docker ps --format 'table {{.Names}}\t{{.Status}}'
kubectl config view --minify --context kind-dc-east | grep server
docker port dc-east-control-plane 6443

Replace NODE with the node that is not Ready. Compare what the kubeconfig thinks the API server address is with the port Docker actually published.

Destroys that data center and forgets it. Rebuilding takes minutes. Resetting should feel cheap; you will do it often.

What you learned

  • A Kubernetes cluster is a control plane plus worker nodes. ECS only ever showed you the workers.
  • kind's nodes are containers, which is how one laptop hosts two "data centers".
  • A kubectl context selects which cluster you are talking to.
  • Each system pod owns one job: API, state, scheduling, reconciliation, service networking, DNS.

Check yourself

1. In this lab, what is each "bare-metal host" of a data center, really?

Each entry under nodes: in the kind config becomes one Docker container with its own kubelet and container runtime. That nesting is exactly how one laptop can host two "data centers".

2. Why do the labs always pass --context instead of relying on kubectl config use-context?

Both approaches work. But with two data centers, a forgotten use-context means commands silently land in the wrong cluster. Explicit --context makes the target visible in every command you type.

3. A new pod is created. Which component picks the node it lands on, and what does ECS call that job?

The scheduler's one job is choosing a node for each new pod, which ECS calls task placement. The API server is the front door, and the controller manager drives actual state toward desired state.

4. What does extraPortMappings in dc-east.yaml set up?

Node containers are normally unreachable from your laptop. extraPortMappings pre-opens 8080/8443 on the host into the control-plane node's 80/443, so phase 1 traffic has a way in. Pod-to-pod networking is kindnet's job, and kind publishes the API server port to your laptop and writes credentials into your kubeconfig, so kubectl can already reach and authenticate to the cluster.

5. If etcd lost its data, what would the cluster forget?

etcd is the database holding desired and observed state. Images live on nodes and DNS lives in coredns, but the record of what the cluster is supposed to look like lives only in etcd.

6. Which half of a Kubernetes cluster did ECS and Cloud Run never let you see?

ECS only ever showed you the workers (EC2 container instances); the control plane exists but is AWS-managed and invisible, and Cloud Run hides everything. Here the control plane runs in a container you can watch.
