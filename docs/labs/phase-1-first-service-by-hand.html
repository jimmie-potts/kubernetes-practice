Phase 1: First Service by hand

Goal: Acme's chat Service serving completions in dc-east through ingress-nginx, built object by object with raw kubectl. Ticket #3.

Everything happens in dc-east; dc-west sits idle until phase 4. Objects land in the default namespace for now. Tenant walls arrive in phase 3.

The path you are building, outside in:

curl chat.acme.dc-east.localtest.me:8080
  -> 127.0.0.1:8080 (localtest.me wildcard DNS)
  -> Docker port map to the control-plane node's port 80
  -> ingress-nginx pod (reads Ingress objects, routes by hostname)
  -> chat Service (stable address for the pods)
  -> a chat pod (fake-inference container)

Each object below exists to make one hop of that path work.

Step 1: A pod, alone

Ask for a single pod running the fake-inference image:

kubectl --context kind-dc-east run chat-solo --image=forge/fake-inference:0.1.0

What will the STATUS column show, and why? Think about where the node goes looking for the image.

kubectl --context kind-dc-east get pods
Expected output

Status shows ErrImagePull or ImagePullBackOff.

This failure is the lesson: the node's container runtime went looking for forge/fake-inference:0.1.0 and found nothing, because the image exists only in your laptop's Docker. The cluster cannot see it.

Why this maps to ECS

In ECS terms, you asked for a task whose image was never pushed to ECR.

Forge has no registry, so kind offers a shortcut that copies an image onto every node:

docker build -t forge/fake-inference:0.1.0 --build-arg APP_VERSION=0.1.0 services/fake-inference/
kind load docker-image forge/fake-inference:0.1.0 --name dc-east

Now watch, touching nothing else:

kubectl --context kind-dc-east get pods -w
Expected output

Within a minute or two the kubelet retries the pull, finds the image on its own node, and the pod flips to Running. Ctrl-C to stop watching.

(Retries back off, so if you are impatient: delete the pod and run it again.) You fixed the cause; reconciliation did the rest. Talk to the pod through an API-server tunnel:

kubectl --context kind-dc-east port-forward pod/chat-solo 18080:8000

In a second terminal:

curl localhost:18080/healthz
Why port-forward is not the production path

port-forward tunnels through the control plane. It is a debug door, not a production path; customer traffic will use the ingress you build in step 4.

Ctrl-C the port-forward, then see why a bare pod is not enough:

kubectl --context kind-dc-east delete pod chat-solo
kubectl --context kind-dc-east get pods
Expected output

Gone, and nothing brings it back.

No object in the cluster says "there should be a chat pod", so no control loop disagrees with an empty list. Deployments fix that.

Step 2: A Deployment keeps them alive

Create the file deploy/tenants/acme/chat-deployment.yaml yourself (typing it is the point):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: chat
  labels:
    app: chat
    tenant: acme
spec:
  replicas: 2
  selector:
    matchLabels:
      app: chat
  template:
    metadata:
      labels:
        app: chat
        tenant: acme
    spec:
      containers:
        - name: fake-inference
          image: forge/fake-inference:0.1.0
          ports:
            - containerPort: 8000
          env:
            - name: MODEL_NAME
              value: acme-chat-1
Why this shape: the ECS reading

Read it as an ECS service fused with its task definition: template is the task definition (image, ports, env), replicas is desired count, and selector is the glue. The selector must match the template's labels; that is the contract by which the Deployment recognizes which pods are "its own".

kubectl --context kind-dc-east apply -f deploy/tenants/acme/chat-deployment.yaml
kubectl --context kind-dc-east get pods
Expected output

Two pods with generated names like chat-7c9f8b6d4-x2klm.

What the middle hash names

The middle hash names the ReplicaSet, an object the Deployment manages for you; you will meet it properly during rollouts in phase 2.

Docs: Deployments · ReplicaSets

On your own: prove the Deployment heals

Goal: delete one of the two chat pods and show that a replacement appears without your help. This is ticket #3's acceptance test, and step 1 and step 2 already gave you every command it needs: list pods, delete a pod, watch pods.

Prove it:

Will the replacement pod carry the deleted pod's name, or a new one?

kubectl --context kind-dc-east get pods -l app=chat
Expected output

Two Running pods, one of them seconds old with a new random suffix.

Show the commands

Delete one pod and watch in the same line:

kubectl --context kind-dc-east delete $(kubectl --context kind-dc-east get pods -l app=chat -o name | head -1) & kubectl --context kind-dc-east get pods -w

A replacement appears while the old one terminates: actual state dropped to one, desired said two, a control loop acted. The old pod may show Completed for a moment before it disappears. Ctrl-C when it settles.

This is the same reconciliation that recovered your image pull, and it never sleeps.

Step 3: A Service gives them one address

Two pods, two private IPs, and both change every time a pod is replaced:

kubectl --context kind-dc-east get pods -o wide

Nothing should ever chase pod IPs. Create deploy/tenants/acme/chat-service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: chat
  labels:
    tenant: acme
spec:
  selector:
    app: chat
  ports:
    - port: 80
      targetPort: 8000
kubectl --context kind-dc-east apply -f deploy/tenants/acme/chat-service.yaml

CLUSTER-IP will show an address. Is it a pod's IP, a node's IP, or something else?

kubectl --context kind-dc-east get svc chat

The CLUSTER-IP is a stable virtual address; kube-proxy (phase 0) programs every node to route it to whichever chat pods exist right now. It is a target group plus service discovery in one object. Prove the DNS half from inside the cluster, since a ClusterIP is not reachable from your laptop:

kubectl --context kind-dc-east run tester --rm -i --restart=Never --image=curlimages/curl -- curl -s http://chat/healthz
Expected output

{"status":"ok"}, followed by a kubectl notice that the session is recorded in container logs and a line saying the tester pod was deleted. Both lines are kubectl housekeeping for --rm -i.

That pod resolved the name chat through coredns, hit the Service IP, and reached a pod. Services finding each other by name is how tenant microservices will talk in later phases.

Docs: Service · DNS for Services and Pods

Step 4: ingress-nginx, the shared front door

The Service is reachable only inside the cluster. Enter the nginx from the interview diagram, installed like any workload:

kubectl --context kind-dc-east apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml

One correction before it can work here. Pin the controller to the port-mapped node, which our config labeled ingress-ready=true in phase 0:

Why the controller needs pinning

Our kind config publishes ports 80/443 of the control-plane node only, but since v1.13 this manifest no longer pins the controller to a labeled node, so it may land on a worker nobody can reach (the trap recorded in ADR-0005).

kubectl --context kind-dc-east -n ingress-nginx patch deployment ingress-nginx-controller -p '{"spec":{"template":{"spec":{"nodeSelector":{"ingress-ready":"true","kubernetes.io/os":"linux"}}}}}'

On real bare metal this is a real decision: the edge proxy must run on the machines whose ports face the world. Wait for it:

kubectl --context kind-dc-east -n ingress-nginx rollout status deployment/ingress-nginx-controller --timeout=180s

Docs: kind: ingress · ingress-nginx installation guide · Assigning pods to nodes

Step 5: An Ingress routes your hostname

Create deploy/tenants/acme/chat-ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: chat
  labels:
    tenant: acme
spec:
  ingressClassName: nginx
  rules:
    - host: chat.acme.dc-east.localtest.me
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: chat
                port:
                  number: 80

An Ingress is an ALB listener rule: "this hostname goes to that Service".

Why no packet touches the control plane

The controller watches these objects through the API server and rewrites its own nginx config; no packet ever passes through the control plane.

kubectl --context kind-dc-east apply -f deploy/tenants/acme/chat-ingress.yaml

The moment of truth (*.localtest.me resolves to 127.0.0.1, and 8080 is dc-east's published port):

curl http://chat.acme.dc-east.localtest.me:8080/readyz
Expected output

{"status":"ready","model":"acme-chat-1"}. A 404 page from nginx means it has not loaded the new Ingress yet; try again in a few seconds. The path is /readyz rather than /healthz on purpose: ingress-nginx answers /healthz itself, for any hostname, so that path proves nothing about your route.

curl -s -X POST http://chat.acme.dc-east.localtest.me:8080/v1/completions -H 'Content-Type: application/json' -d '{"prompt":"hello forge"}'

A completion, served by Acme's model, through Forge's front door. One shared nginx will serve every Tenant this way, split by hostname; that is the multi-tenant carve-up from ADR-0005.

Docs: Ingress

Step 6: The crack in the wall

fake-inference takes about ten seconds to "load its model" after starting, and right now Kubernetes has no idea. Catch it in the act. Trigger a restart of all pods, then hammer the endpoint:

kubectl --context kind-dc-east rollout restart deployment chat

What status codes will the fifteen requests return, and in what pattern?

for i in $(seq 1 15); do curl -s -o /dev/null -w '%{http_code} ' -X POST http://chat.acme.dc-east.localtest.me:8080/v1/completions -H 'Content-Type: application/json' -d '{"prompt":"hi"}'; sleep 1; done; echo
Expected output

Mixed in with the 200s you will see 503s.

Traffic reached pods whose model was still loading, because nobody told Kubernetes what "ready" means for this container. For an inference platform, model loading time is the whole game. Readiness probes fix this in phase 2, and you have now seen exactly why they exist.

Drill: Acme's requests are failing

The request path has five hops, and any one of them can drift. This drill breaks one of them at random in dc-east. Find it hop by hop, fix it, and confirm with the check.

scripts/drills/phase-1.sh break

Run the completions curl from step 5 and the checkpoint. Before opening any hint, state the symptom in one sentence, including the HTTP status code nginx returned.

Hint 1: where to look

Walk the path from the outside in, and let nginx's status code tell you how far the request got. A 503 means nginx had nowhere to send it: either the Ingress points at a Service that does not exist, or the Service has no endpoints because its selector matches no pods. A 502 means nginx reached a pod address and was refused, which points at a port. The objects are all still there; one field in one of them no longer matches your files.

Hint 2: what to run 
kubectl --context kind-dc-east describe ingress chat
kubectl --context kind-dc-east describe svc chat
kubectl --context kind-dc-east get endpointslices -l kubernetes.io/service-name=chat
kubectl --context kind-dc-east get pods -l app=chat -o wide --show-labels

Endpoints are the truth about where a Service will forward. None at all means the selector matched nothing. Addresses on a port the container does not listen on mean the targetPort drifted. Compare every field with your three files in deploy/tenants/acme/.

What you learned

  • Nothing in Kubernetes "starts a container"; you declare objects and control loops make them true. The image-pull recovery and the pod replacement were the same mechanism.
  • Pod, Deployment, Service, Ingress each solve one failure of the previous layer: death, identity, reachability.
  • The Deployment selector and pod labels are a contract, not decoration.
  • The ingress controller is a workload like any other; only node placement and published ports make it the front door.
  • port-forward goes through the control plane; ingress traffic never does.

Next: phase 2 (#4), where chat gets probes, config from ConfigMaps and Secrets, resource requests, autoscaling, and a rollback.

Check yourself

1. Your kubectl run chat-solo pod sits in ErrImagePull. What actually went wrong?

Nodes pull images with their own container runtime, which knows nothing about your laptop's Docker daemon. In ECS terms: a task whose image was never pushed to ECR. kind load copies the image onto every node, and the kubelet's retry then succeeds.

2. After kind load, the pod flips to Running even though you touched nothing else. Why?

You fixed the cause; a retry loop did the rest. It is the same mechanism that later replaces a deleted Deployment pod. Control loops never stop comparing desired state to actual state.

3. Deleting chat-solo left the cluster empty forever, but deleting a Deployment-managed pod got it replaced within seconds. What makes the difference?

replicas: 2 is standing desired state. When actual drops to one, a control loop acts. A bare pod leaves nothing behind that says "there should be a chat pod".

4. Why must the Deployment's selector match the pod template's labels?

The selector and the pod labels are a contract, not decoration. It is the glue between "keep two of these" and the actual pods that count toward two.

5. Why did the ingress-nginx controller need the nodeSelector patch in this cluster?

Since v1.13 the kind manifest no longer pins the controller to a labeled node (the ADR-0005 trap). The controller runs fine on a worker, but no outside traffic can reach it there. The edge proxy must sit on the machine whose ports face the world.

6. In step 6, some requests return 503 right after the rollout restart. Why?

fake-inference takes about ten seconds to "load its model", and Kubernetes routed traffic to it anyway. Readiness probes in phase 2 will keep unready pods out of rotation. You have now seen exactly why they exist.

Explain pod, Deployment, Service, and Ingress to an ECS engineer: one sentence each, naming the ECS twin.

Compare with a model answer

Pod: one running set of containers with its own IP, the ECS task. Deployment: keeps N copies of a pod template alive and rolls them when the template changes, the ECS service with its desired count. Service: one stable address and DNS name for whichever pods match a label selector right now, a target group plus service discovery. Ingress: a hostname routing rule that the shared nginx controller reads, an ALB listener rule.

A teammate says: "The pod is Running, so the deploy worked." Using step 6, explain what Running does not tell you.

Compare with a model answer

Running means the container process started, nothing more. In step 6 the pods were Running while the model was still loading, and traffic reached them and got 503s. Running says nothing about being ready to serve; Kubernetes needs a readiness probe to know that, which is what phase 2 adds.
